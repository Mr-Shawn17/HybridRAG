> 日期：2026-09-06
> 目的：把每个分叉点的选项、代价、适配你的硬件与目标讲清楚，供决策。**本文档不含实现代码。**

## 0. 已确认的前提（来自三轮沟通）

| 项 | 你的选择 | 对选型的影响 |
|---|---|---|
| 语料/场景 | 公开数据集做技术验证 | 需要对照实验和指标数字，选型要"能拆开看" |
| 部署形态 | 本地检索 + 云 LLM | embedding/reranker 本地跑，生成走 API |

| **基准集** | **C-MTEB 检索子任务** | 有公开榜单可对标；但需避开超大语料库子任务（见 §8.2） |
| **交付形态** | **Gradio Web UI** | 需要能展示对照实验结果的界面 |

## 1. 必须先解决的目标冲突

你的两个选择方向不一致：

- **「公开数据集做技术验证」** → 本质是研究任务，需要 dense / BM25 / 混合 / 混合+重排 四组干净对照，要能改融合公式、改切分参数、看中间结果。
- **「快速做出能用的东西」** → 本质是交付任务，用 RAGFlow / Dify 几小时出 Web UI，但融合策略、切分策略被平台封装，拿不到对照数据。

这两件事不能同时最大化。三种收敛方式：

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 以验证为主**（建议） | 用 LlamaIndex 半自研，自己控制切分/召回/融合/重排，跑出对照数字。UI 用 Gradio 凑一个 | 出"能用的东西"要 1~2 周而非 1 天 |
| B. 以交付为主 | RAGFlow 一把梭，先有个能用的知识库问答 | 学不到原理，对照实验做不了 |
| C. 分两阶段 | 先 LlamaIndex 快速跑通可演示版（3~5 天），再把切分/融合/重排逐个替换为自研实现做对照 | 总工作量最大，但两个目标都能达成 |

> **C 是最贴合你「快速做出能用的东西 + 课程学习背景」的路线**，但要接受总工期更长。这个决策留到最后一轮确认。

## 2. 检索引擎选型

这是最重的一个决策。四个候选：

### 2.1 能力对比

| 维度 | LanceDB / Chroma | Milvus 2.5+ | Qdrant | Elasticsearch / OpenSearch |
|---|---|---|---|---|
| 稠密向量 | 支持（LanceDB 用 IVF_PQ/HNSW） | 支持，索引类型最全 | 支持，HNSW 成熟 | 支持（8.x kNN） |
| 稀疏/BM25 | LanceDB 2024+ 支持 BM25；Chroma 需外挂 rank_bm25 | **原生 Sparse-BM25**，文本直接进出 | 支持稀疏向量 + IDF modifier | **BM25 最成熟**，业界标杆 |
| 中文分词 | 需自己做（jieba） | **内置 chinese analyzer（jieba + cnalphanumonly）**，2.5.11+ 可 run_analyzer 验证 | 需自己做分词后传入 | IK 分词插件（需装，版本对应易踩坑） |
| 混合检索融合 | 需自己写 RRF | **内置 RRFRanker / WeightedRanker** | **内置 RRF prefetch + 分支权重** | 内置 RRF（8.9+） |
| 元数据过滤 | 基础 | 强（BitMap/Array/倒排索引，2.5 大幅提速） | 强（payload filter 性能好） | 最强（DSL 表达力无上限） |
| 运维成本 | **零**（嵌入式，一个文件/目录） | 中（需 Docker，standalone 约 4~8G 内存） | 中（单二进制或 Docker，资源占用低于 Milvus） | **高**（JVM 调优、分片、集群） |
| 内存占用（10 万 chunk） | 数百 MB | 2~4 GB | 1~2 GB | 4 GB+ 起步 |
| 迁移到分布式 | 不支持 | **原生支持**（standalone → distributed 平滑） | 支持（分片+副本） | 原生 |
| 学习曲线 | 最低 | 中 | 中低 | 高 |

### 2.2 关键事实核查结果

- **Milvus 2.5+ 已原生支持全文检索**：内置 Sparse-BM25（基于 tantivy 分词器），支持"Doc in, Doc out"——直接插入原始文本，服务端自动分词、生成稀疏向量、动态更新 TF/IDF。**内置 `chinese` analyzer = jieba 分词器 + cnalphanumonly 过滤器**，且提供 `run_analyzer()` 方法可以在建索引前验证分词结果。这解决了 Milvus 早年在中文全文检索上的最大短板。
  - 限制：全文检索**不支持 Milvus Lite**，需要 Standalone 或 Distributed（即需要 Docker 部署）。
- **Qdrant** 的混合检索通过 `query_points` + 两个 `Prefetch` + `FusionQuery(fusion=RRF)` 一次请求完成，稀疏向量支持 `Modifier.IDF`。但**中文分词需要自己在客户端做**（jieba 分好词再传入），Qdrant 本身不带中文分词器。
- **RRF 的 k=60 默认值**来自 2009 SIGIR 原始论文，跨领域表现稳定。**在没有 ≥200 条标注查询之前不要调 k**，否则只是在追噪声。这一点对你很重要——你的评测集规模决定了哪些参数可调、哪些不能调。

### 2.3 适配你的情况

| 引擎 | 适配度 | 理由 |
|---|---|---|
| **Milvus 2.5+** | 高 | 内置中文分词是决定性优势（中文混合检索最常见的翻车点被平台解决了）；融合、过滤全内置；standalone→distributed 迁移平滑，符合"保留向上迁移空间" |
| **Qdrant** | 高 | 资源占用低、API 干净、混合检索一次请求搞定；但中文分词要自己写（其实也不难，jieba 一行） |
| LanceDB | 中 | 零运维很香，但 BM25 支持较新、生态与文档不如前两者，做对照实验时可控性反而不如 Milvus |
| Elasticsearch | 低（当前阶段） | BM25 最强，但 JVM + IK 插件 + 内存开销，对"4~6G 显存的单机 + 快速验证"太重 |

> **倾向：Milvus 2.5+（中文分词内置）或 Qdrant（轻量、API 优雅）。**
> 注意 Milvus standalone 会额外吃 4~8G 内存，如果你的机器内存 ≤16G 且 GPU 显存只有 4~6G，Qdrant 的资源占用更友好。

## 3. 稀疏检索路线

| 路线 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **经典 BM25** | 词频-逆文档频率 | 零训练、可解释（能看到命中哪个词）、中文配好分词就能用 | 无语义扩展，同义词/改写召回差 |
| **Learned sparse（SPLADE / BGE-M3 sparse）** | 模型学习词项权重，可产生"文档里没出现但语义相关"的词项权重 | 召回优于 BM25，仍保留倒排索引的可解释性 | 需模型推理（吃显存/算力），中文效果依赖模型训练语料 |
| **两者对照** | 同一份数据建两套稀疏索引，比较指标 | 能得出"learned sparse 在中文上到底值不值"的结论 | 工作量翻倍 |

**BGE-M3 的特殊性**：单次前向传播同时输出 dense / sparse / multi-vector(ColBERT) 三种表示。也就是说，如果你选 BGE-M3 做 embedding，**learned sparse 这一路是免费的**，不用额外部署 SPLADE。这对做对照实验非常划算。

## 4. Embedding 与 Reranker（受 4~6G 显存强约束）

### 4.1 显存事实核查

| 模型 | 参数量 | FP16 显存 | 4~6G 显存可行性 |
|---|---|---|---|
| bge-small-zh-v1.5 | 24M | ~0.1 GB | 轻松 |
| bge-large-zh-v1.5 | 326M | ~0.7 GB | 轻松 |
| **BGE-M3** | 568M | ~1.2~2 GB | **可行**，但同时跑 reranker 会紧张 |
| **bge-reranker-v2-m3** | 568M | **~1.6 GB**（FP16） | 单独跑可行 |
| Qwen3-Embedding-0.6B | 600M | ~1.3 GB | 可行 |
| Qwen3-Embedding-4B | 4B | ~9 GB | **不可行** |

### 4.2 4~6G 显存的真实约束

关键问题不是"能不能跑"，而是"**能不能同时跑**"：

- BGE-M3（~2G）+ bge-reranker-v2-m3（~1.6G）= **~3.6G**，加上 CUDA 上下文和 PyTorch 开销（约 0.5~1G），**4G 显存会 OOM，6G 勉强可行**。
- 索引阶段只需要 embedding（一次性批处理），查询阶段需要 embedding + reranker。
- **可行的三种解法**：
  1. **模型分时加载**：索引时用 embedding，查询时先卸载 embedding 再加载 reranker（简单但每次查询有加载延迟）
  2. **reranker 走云端 API**：本地只跑 embedding，重排调用硅基流动/阿里百炼的 rerank API（**推荐**，延迟约 100~300ms，成本极低）
  3. **降低精度/候选数**：reranker 用 FP16 且只重排 top 20~30 而非 top 100（bge-reranker-v2-m3 在 RTX 3060 上重排 5 条约 380ms，线性外推 top 30 约 1~2s）

### 4.3 Embedding 候选

| 模型 | 维度 | 中文效果 | 长度上限 | 备注 |
|---|---|---|---|---|
| **BGE-M3** | 1024 | 强 | **8192** | dense+sparse+colbert 三合一，混合检索首选 |
| bge-large-zh-v1.5 | 1024 | 强 | 512 | 纯中文场景够用，长度上限是硬伤 |
| Qwen3-Embedding-0.6B | 1024 | 强 | 32768 | 较新，MTEB 多语言榜首级别 |
| text-embedding-3-large | 3072 | 中上 | 8191 | 云端，中文不如 BGE-M3，但有成本 |
| 云端 BGE-M3 API | 1024 | 强 | 8192 | 硅基流动提供，避开本地显存问题 |

## 5. 融合与重排策略

### 5.1 融合算法

| 算法 | 公式 | 优点 | 缺点 |
|---|---|---|---|
| **RRF** | `score(d) = Σ 1/(k + rank_i(d))`，k 默认 60 | 只看排名不看分数，**彻底绕开量纲问题**，免调参 | 丢失分数信息（第 1 名和第 2 名差距多大不知道） |
| 加权归一化 | `α·norm(dense) + (1-α)·norm(sparse)` | 可调优，保留分数信息 | **BM25 分数无上界且依赖语料统计，余弦相似度在 [-1,1]，两者分布无法直接归一化**；min-max 对离群值敏感，z-score 每次查询都变形 |

> **结论：首选 RRF。** 加权归一化是新手最常踩的坑——直接 `α·vector + (1-α)·bm25` 必然失真。只有在评测集 ≥200 条且需要精细调优时才考虑加权，且必须先做分数标定。

### 5.2 重排（Reranker）

重排是**投入产出比最高的单个改进**：典型能把 Precision@5 提升 10~30%。原因是 cross-encoder 把 query 和 doc 拼在一起过一次 transformer，比双塔 embedding 的距离计算精确得多。

| 模型 | 参数量 | 输入长度 | 部署 |
|---|---|---|---|
| **bge-reranker-v2-m3** | 568M | **8192** | 本地（~1.6G 显存）或云 API |
| Qwen3-Reranker-0.6B | 600M | 32768 | 本地（~1.3G 显存） |
| bce-reranker-base_v1 | ~300M | **512** | 本地更轻，但长度上限是硬伤 |
| Cohere Rerank | - | - | 云 API，中文一般，有成本 |

> **典型流水线参数**：两路各召回 top 50~100 → RRF 融合 → reranker 重排 → 取 top 3~5 进 Prompt。
> 注意：**塞太多 chunk 进 Prompt 会触发 "lost in the middle"**，重排后取 3~5 条通常比 20 条答得更准。

## 6. 开发框架选型

| 框架 | 定位 | 优点 | 缺点 | 适配度 |
|---|---|---|---|---|
| **LlamaIndex** | RAG 专用框架 | RAG 原语最全（Node Parser、Retriever、Reranker、Evaluator 都是一等公民）；QueryEngine/ChatEngine 现成；对照实验容易搭 | 抽象层多，出问题时调试链路长 | **高** |
| LangChain | 通用 LLM 应用框架 | 生态最大，集成最多 | 抽象过重、版本变动频繁、RAG 原语不如 LlamaIndex 精细 | 中 |
| 自研（FastAPI + SDK） | 全手写 | 完全可控、最好调试、代码量其实不大（核心链路 ~500 行） | 所有轮子自己造，工期最长 | 中（若走 §1 方案 C 的第二阶段则高） |
| RAGFlow | 开箱 RAG 平台 | 深度文档解析（DeepDoc）是杀手锏，UI 完整 | 融合/切分策略被封装，拿不到对照数据 | 低（与验证目标冲突） |
| Dify | LLMOps 平台 | 上手最快，可视化编排 | 同上，且检索能力弱于 RAGFlow | 低 |

> **倾向 LlamaIndex**：它在"快速跑通"和"能拆开做对照实验"之间平衡最好。若走 §1 方案 C，第二阶段再把关键模块换成自研实现。

## 7. 切分策略（效果问题的头号根源）

行业经验：**约 60% 的 RAG 效果问题源于切分不当，优先级高于换模型。**

| 策略 | 说明 | 适用 |
|---|---|---|
| 固定窗口 | 按 token 数切，带 overlap（如 512 token / 50 overlap） | baseline，必做对照组 |
| **结构感知** | 按 Markdown 标题层级 / PDF 章节切 | 结构化文档首选 |
| 语义切分 | 用 embedding 相似度找语义断点 | 效果好但慢，索引成本高 |
| **small-to-big** | 检索用小 chunk（精准匹配），返回时给 LLM 大 chunk（完整上下文） | **强烈推荐**，兼顾召回精度与上下文完整性 |
| Sentence Window | 检索单句，返回前后 N 句窗口 | LlamaIndex 内置，实现简单 |

**必须特殊处理的内容**：
- 表格：被通用切分器切碎后检索时永远拼不回来 → 整表作为一个 chunk，或转 Markdown 表格保留结构
- 代码块：按函数/类边界切，不能按 token 数硬切
- 列表/条款：按条目切，保留编号

## 8. 评测方案

### 8.1 指标体系

| 层次 | 指标 | 说明 |
|---|---|---|
| **检索侧** | Recall@K | 前 K 个结果里包含了多少相关文档（K 常取 5/10/20） |
| | MRR | 第一个相关结果的排名倒数的均值 |
| | nDCG@K | 带位置折扣的排序质量，比 Recall 更敏感 |
| | Precision@K | 前 K 个里有多少是相关的 |
| **生成侧** | 忠实度 Faithfulness | 答案是否只基于给定上下文（防幻觉） |
| | 答案相关性 | 答案是否回答了问题 |
| | 上下文精度 | 检索到的上下文是否有用 |

生成侧指标可用 **RAGAS** 框架自动评（需要一个强 LLM 做裁判，走云 API）。

### 8.2 评测集（你选了"用 C-MTEB 检索子任务"）—— 已核查，有重要发现

C-MTEB（Chinese Massive Text Embedding Benchmark）收录 35 个公开数据集，分 6 类任务，其中**检索类 8 个、重排类 4 个**。用它的最大好处是：**有标准化评测脚本 + 公开榜单，你的结果可以直接和 BGE-M3、Qwen3-Embedding 等模型的公开分数对标**，主指标是 nDCG@10。

但核查后发现一个**致命细节：各子任务的语料库（corpus）规模差异极大**，表格里"测试样本数"只是查询数，不代表语料库规模：

| 子任务 | 查询数 | **语料库规模** | 单机可行性（本地 BGE-M3） |
|---|---|---|---|
| **T2Retrieval** | 24,832 | **约 230 万段落**（T2Ranking collection.tsv = 2,303,643） | **不可行**，索引需数天 |
| **MMarcoRetrieval** | 7,437 | **约 880 万段落**（mMARCO 中文版） | **不可行** |
| **DuRetrieval** | 约 4,000 | **约 10 万段落**（corpus 100,001 条，约 91 MB） | **可行**，embedding 约 1~2 小时 |
| CmedqaRetrieval | 3,999 | 约 10 万级 | 可行 |
| **CovidRetrieval** | 949 | **约 6 千条新闻** | **最快**，几分钟建完索引 |
| EcomRetrieval | 1,000 | 小（万级） | 可行，迭代快 |
| MedicalRetrieval | 1,000 | 小（万级） | 可行 |
| VideoRetrieval | 1,000 | 小（万级） | 可行 |

> **结论：不要用 T2Retrieval / MMarcoRetrieval 做主评测集**（这是最多人踩的坑，看查询数不多就下了，结果卡在语料库索引上）。
>
> **推荐的三层组合**：
> - **快速迭代层**：`CovidRetrieval`（949 查询 / 约 6 千语料）——建索引几分钟，改一次参数就能重跑，用于调试链路与切分策略
> - **主评测层**：`DuRetrieval`（约 4,000 查询 / 约 10 万语料）——规模适中、真实搜索引擎数据，nDCG@10 可与公开榜单对标
> - **领域泛化层**（可选）：`EcomRetrieval` + `MedicalRetrieval`（各 1,000 查询）——验证混合检索在不同领域是否都有效，尤其电商场景专有名词多，是 BM25 那一路最能体现价值的地方
>
> 查询数 4,000 + 1,000 + 1,000 均**远超 RRF 参数调优所需的 200 条阈值**，因此这套数据足以支撑融合权重的调优实验（这是选 C-MTEB 相比自建小评测集的最大优势）。

**重排任务的评测**（评 reranker 增益）另有 4 个子任务：`T2Reranking`（24,382）、`MMarcoReranking`（7,437）、`CMedQAv1`（2,000）、`CMedQAv2`（4,000）。这类任务是"给定查询和一批候选段落，重新排序"，**语料库已给定不需自己索引**，因此即使 T2Reranking 规模大也可行——它正好适合评 bge-reranker-v2-m3 云 API 的效果。

**自建语料部分**（你选了"两者都做"）：
- 用途是验证端到端问答体验（基准集只能评检索，评不了生成质量）
- 需人工标注 50~100 条 query → 相关文档
- 建议直接用你八斗课程的讲义/笔记，或某开源项目的中文文档——既贴近真实使用，又便于你自己判断检索结果对不对
- 生成侧指标（忠实度、答案相关性）用 **RAGAS** 框架自动评，裁判 LLM 走云 API

### 8.3 对照实验矩阵（这是"技术验证"的核心交付物）
